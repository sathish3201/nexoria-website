Object Design Field Guide

OOP fundamentals with a beginner walkthrough, the five SOLID principles, and six patterns you'll actually meet in interviews and in production — each shown before and after, with a UML diagram and working code in four languages.

01 / FoundationsThe Four Pillars of OOP

Every pattern below is built from four ideas. React has no classes in practice, but each pillar still maps onto components, hooks, and props — noted alongside.

PillarMeansPython / Java / C#React equivalent
Encapsulation Bundle state with the behavior that guards it; hide internals. Private fields (__x, private) behind public methods. Component state via useState stays inside the component; only props/callbacks cross the boundary.
Abstraction Expose what, hide how. Abstract base classes / interfaces (ABC, interface). A custom hook (useAuth()) hides fetch/storage details behind a simple call.
Inheritance Derive a specialized type from a general one, reusing its shape. class Dog(Animal), extends. Rare and discouraged — composition via wrapping components does this job instead.
Polymorphism One interface, many concrete behaviors, selected at runtime. Method overriding, interface implementations. Rendering different components/branches based on a type prop or discriminated union.
Interview framing

When asked "explain OOP," lead with encapsulation and polymorphism — they're what SOLID and every pattern below actually lean on. Inheritance is the pillar most patterns here deliberately avoid in favor of composition.

02 / FoundationsOOP in Practice — a Beginner Walkthrough

If you've never written a class before, start here. Below is the same small program — tracking a library book — written twice: first as loose variables and functions (how most people start), then as a class. Run both in your head; the outputs match, but only one of them scales.

Step 1 — the problem, without OOP

Plain variables and functions floating separately. Nothing stops you from passing the wrong dictionary to the wrong function, and every function needs to re-check what state the book is in.

Before — no OOP
# Book data and behavior are disconnected.
# Any function can mutate any dict, in any shape.
book = {"title": "Dune", "is_checked_out": False}

def check_out(b):
    if b["is_checked_out"]:
        raise ValueError("Already out")
    b["is_checked_out"] = True

def return_book(b):
    b["is_checked_out"] = False

# Nothing enforces this contract — any code anywhere
# could write book["is_checked_out"] = "yes" and break it.
check_out(book)
print(book["is_checked_out"])  # True
Works for one book. Add a second book type (DVD, magazine) and every function needs new branches to handle each shape.
After — with OOP
# State (title, is_checked_out) and the behavior that
# guards it now live in one place: the class.
class Book:
    def __init__(self, title):
        self.title = title
        self._is_checked_out = False   # encapsulated

    def check_out(self):
        if self._is_checked_out:
            raise ValueError("Already out")
        self._is_checked_out = True

    def return_book(self):
        self._is_checked_out = False

    def is_available(self):
        return not self._is_checked_out

dune = Book("Dune")
dune.check_out()
print(dune.is_available())  # False
The rule "can't check out an already-checked-out book" lives inside Book itself — impossible to bypass by accident.

Step 2 — polymorphism removes the branching

Now add a second kind of item: a DVD, which has a different loan period. Without OOP you'd add an if item_type == "dvd" check everywhere. With OOP, each class knows its own rule — the calling code doesn't change at all.

class LibraryItem:
    def __init__(self, title):
        self.title = title

    def loan_period_days(self):
        raise NotImplementedError

class Book(LibraryItem):
    def loan_period_days(self):
        return 21

class Dvd(LibraryItem):
    def loan_period_days(self):
        return 7

# This function never checks "what type is it?" — it just asks.
def due_date_message(item):
    return f"{item.title} is due in {item.loan_period_days()} days"

for item in [Book("Dune"), Dvd("Arrival")]:
    print(due_date_message(item))
# Dune is due in 21 days
# Arrival is due in 7 days
public abstract class LibraryItem {
    protected final String title;
    protected LibraryItem(String title) { this.title = title; }
    public abstract int loanPeriodDays();
}

public class Book extends LibraryItem {
    public Book(String title) { super(title); }
    public int loanPeriodDays() { return 21; }
}

public class Dvd extends LibraryItem {
    public Dvd(String title) { super(title); }
    public int loanPeriodDays() { return 7; }
}

// Never checks "what type is it?" — it just asks.
static String dueDateMessage(LibraryItem item) {
    return item.title + " is due in " + item.loanPeriodDays() + " days";
}
public abstract class LibraryItem
{
    public string Title { get; }
    protected LibraryItem(string title) => Title = title;
    public abstract int LoanPeriodDays();
}

public class Book : LibraryItem
{
    public Book(string title) : base(title) { }
    public override int LoanPeriodDays() => 21;
}

public class Dvd : LibraryItem
{
    public Dvd(string title) : base(title) { }
    public override int LoanPeriodDays() => 7;
}

// Never checks "what type is it?" — it just asks.
string DueDateMessage(LibraryItem item) =>
    $"{item.Title} is due in {item.LoanPeriodDays()} days";
// React has no classes here — polymorphism becomes each
// item "knowing" its own loan period via a lookup or method
// on a plain object, and the component never branches on type.

const book = { title: "Dune", loanPeriodDays: () => 21 };
const dvd  = { title: "Arrival", loanPeriodDays: () => 7 };

// Never checks "what type is it?" — it just calls the method.
function DueDateBadge({ item }) {
  return <span>{item.title} is due in {item.loanPeriodDays()} days</span>;
}

[book, dvd].map(item => <DueDateBadge key={item.title} item={item} />);
What actually changed

No new syntax trick — the loan period rule simply moved from "a check the caller has to remember" into "a fact the object can answer about itself." That single move is the seed every SOLID principle and every pattern below grows out of.

S — Single Responsibility Principle

A class should have exactly one reason to change. Report that formats, saves, and prints has three reasons — split each concern into its own class.

Before: one Report class formats text, writes files, and prints — edit any of the three and you risk breaking the others. After: Report, ReportPrinter, ReportFileSaver each change for exactly one reason. See the code below.
Report holds data only; printing and saving live in their own single-purpose classes.
class Report:
    # Holds data + formatting only. Nothing else.
    def __init__(self, title, content):
        self.title, self.content = title, content

    def generate_text(self):
        return f"{self.title.upper()}\n\n{self.content}"

class ReportPrinter:
    def print(self, text):
        print(text)

class ReportFileSaver:
    def save(self, text, filename):
        with open(filename, "w") as f:
            f.write(text)
public class Report {
    private final String title, content;
    // Holds data + formatting only. Nothing else.
    public String generateText() {
        return title.toUpperCase() + "\n\n" + content;
    }
}

public class ReportPrinter {
    public void print(String text) { System.out.println(text); }
}

public class ReportFileSaver implements ReportSaver {
    public void save(String text, String filename) throws IOException {
        try (FileWriter w = new FileWriter(filename)) { w.write(text); }
    }
}
public class Report
{
    // Holds data + formatting only. Nothing else.
    public string Title { get; }
    public string Content { get; }

    public string GenerateText() =>
        $"{Title.ToUpper()}\n\n{Content}";
}

public class ReportPrinter
{
    public void Print(string text) => Console.WriteLine(text);
}

public class ReportFileSaver : IReportSaver
{
    public void Save(string text, string filename) =>
        File.WriteAllText(filename, text);
}
// Data + formatting lives in a pure function / hook,
// not tangled into the component that renders it.
function formatReport(title, content) {
  return `${title.toUpperCase()}\n\n${content}`;
}

// Rendering is its own concern.
function ReportView({ title, content }) {
  return <pre>{formatReport(title, content)}</pre>;
}

// Persistence is its own concern (a hook, not the component).
function useSaveReport() {
  return function save(text, filename) {
    return fetch(`/api/reports/${filename}`, { method: "PUT", body: text });
  };
}

O — Open/Closed Principle

Open for extension, closed for modification. Add a new report format by adding a new class, not by editing an existing one with another if format == "json" branch.

Before: one saver class with a growing if format == "text" / "json" / "xml" ladder — every new format edits code that already works and already shipped. After: a ReportSaver contract; each format is its own class, added without touching the others.
Both savers implement one contract; a third format is a new box, not a diff to these two.
from abc import ABC, abstractmethod

class ReportSaver(ABC):
    @abstractmethod
    def save(self, report, filename): ...

class TextFileSaver(ReportSaver):
    def save(self, report, filename):
        with open(filename, "w") as f:
            f.write(report.generate_text())

# New format = new class. TextFileSaver never changes.
class JsonFileSaver(ReportSaver):
    def save(self, report, filename):
        json.dump({"title": report.title}, open(filename, "w"))
public interface ReportSaver {
    void save(Report report, String filename) throws IOException;
}

public class TextFileSaver implements ReportSaver {
    public void save(Report r, String filename) throws IOException {
        try (FileWriter w = new FileWriter(filename)) { w.write(r.generateText()); }
    }
}

// New format = new class. TextFileSaver never changes.
public class JsonFileSaver implements ReportSaver {
    public void save(Report r, String filename) throws IOException { /* ... */ }
}
public interface IReportSaver
{
    void Save(Report report, string filename);
}

public class TextFileSaver : IReportSaver
{
    public void Save(Report r, string filename) =>
        File.WriteAllText(filename, r.GenerateText());
}

// New format = new class. TextFileSaver never changes.
public class JsonFileSaver : IReportSaver
{
    public void Save(Report r, string filename) => /* ... */;
}
// The "interface" is just a function shape: (report, filename) => void
const saveAsText = (report, filename) =>
  writeFile(filename, formatReport(report));

// New format = new function. saveAsText never changes.
const saveAsJson = (report, filename) =>
  writeFile(filename, JSON.stringify(report));

// Component depends on whichever strategy is passed in.
function SaveButton({ report, filename, saveStrategy }) {
  return <button onClick={() => saveStrategy(report, filename)}>Save</button>;
}

L — Liskov Substitution Principle

Any subtype must be swappable for its base type without breaking the caller. A ReadOnlySaver that throws on save() breaks every caller that trusted the base contract.

Before: every saver must implement save(), even a read-only one that can't — it throws at runtime, surprising any caller that trusted the contract. After: a read-only class only ever claims the interface it can honor.
Violation

One fat interface (save() + load()) forces a read-only class to implement a method it can't honor — it throws instead.

Fix

Split into narrow Readable / Writable interfaces. A class only implements what it can truly do — the broken substitution becomes unrepresentable.

# Narrow interfaces instead of one fat ReportSaver
class Readable(ABC):
    @abstractmethod
    def load(self, filename): ...

class Writable(ABC):
    @abstractmethod
    def save(self, text, filename): ...

class TextFileSaver(Readable, Writable):
    def save(self, text, filename): ...
    def load(self, filename): ...

# Only claims Readable — no save() to violate.
class ReadOnlyTextSource(Readable):
    def load(self, filename): ...
public interface Readable { String load(String filename); }
public interface Writable { void save(String text, String filename); }

public class TextFileSaver implements Readable, Writable {
    public void save(String t, String f) { /* ... */ }
    public String load(String f) { /* ... */ }
}

// Only claims Readable — no save() to violate.
public class ReadOnlyTextSource implements Readable {
    public String load(String f) { /* ... */ }
}
public interface IReadable { string Load(string filename); }
public interface IWritable { void Save(string text, string filename); }

public class TextFileSaver : IReadable, IWritable
{
    public void Save(string t, string f) { /* ... */ }
    public string Load(string f) => /* ... */;
}

// Only claims IReadable — no Save() to violate.
public class ReadOnlyTextSource : IReadable
{
    public string Load(string f) => /* ... */;
}
// LSP in React shows up in prop contracts: a component that
// promises onSave but sometimes can't call it breaks callers.

// Broken: EditableList always expects onSave, but a read-only
// mode silently no-ops it — surprising to any caller.
function BrokenList({ items, onSave, readOnly }) { /* ... */ }

// Fixed: split into two components with honest prop contracts.
function ReadOnlyList({ items }) { /* renders only */ }
function EditableList({ items, onSave }) { /* onSave always safe to call */ }

I — Interface Segregation Principle

No client should depend on methods it doesn't use. This is the fix that made LSP hold above — Readable and Writable are the segregated interfaces in place of one bloated ReportSaver.

Before: one fat ReportSaver interface bundling save() and load() — implementers are forced to stub out methods they don't need. After: narrow Readable / Writable interfaces, implemented independently.
A read-only source implements only Readable — it is never forced to carry Writable's contract.
Rule of thumb

If implementers keep leaving methods empty or throwing "not supported," the interface is too fat. Split along what's actually always used together.

D — Dependency Inversion Principle

High-level code should depend on abstractions, not concrete low-level classes. A ReportService should take any ReportSaver via its constructor, not hardcode new TextFileSaver() inside itself.

Before: ReportService does new TextFileSaver() internally — swapping formats means editing ReportService itself. After: the saver is passed into the constructor; ReportService only knows the abstraction.
ReportService never names a concrete saver — the composition root decides which one to inject.
class ReportService:
    # Depends on the ReportSaver abstraction, injected in.
    def __init__(self, printer, saver: ReportSaver):
        self.printer, self.saver = printer, saver

    def publish(self, report, filename):
        self.printer.print(report.generate_text())
        self.saver.save(report, filename)

# Composition root chooses the concrete type
service = ReportService(ReportPrinter(), JsonFileSaver())
public class ReportService {
    private final ReportPrinter printer;
    private final ReportSaver saver; // abstraction, injected

    public ReportService(ReportPrinter printer, ReportSaver saver) {
        this.printer = printer; this.saver = saver;
    }

    public void publish(Report r, String filename) throws IOException {
        printer.print(r.generateText());
        saver.save(r, filename);
    }
}
// Composition root chooses the concrete type
new ReportService(new ReportPrinter(), new JsonFileSaver());
public class ReportService
{
    private readonly ReportPrinter _printer;
    private readonly IReportSaver _saver; // abstraction, injected

    public ReportService(ReportPrinter printer, IReportSaver saver)
    {
        _printer = printer; _saver = saver;
    }

    public void Publish(Report r, string filename)
    {
        _printer.Print(r.GenerateText());
        _saver.Save(r, filename);
    }
}
// Composition root (or DI container) chooses the concrete type
new ReportService(new ReportPrinter(), new JsonFileSaver());
// DIP in React = accepting collaborators as props/params,
// not importing a concrete implementation inside the component.

// Depends on the *shape* saveStrategy, not a specific function.
function ReportPublisher({ report, filename, saveStrategy }) {
  useEffect(() => {
    saveStrategy(report, filename);
  }, [report, filename, saveStrategy]);
  return <pre>{formatReport(report.title, report.content)}</pre>;
}

// Composition root (parent / app shell) chooses the concrete strategy
<ReportPublisher report={r} filename="r.json" saveStrategy={saveAsJson} />

04 / StructuralAdapter Pattern

Structural Wraps an incompatible interface

Converts the interface of an existing class into one a client expects, without touching either side. The canonical case: you have a legacy or third-party class and can't change it.

Before — no pattern
# Client code reaches directly into the legacy shape,
# building XML by hand wherever a payment happens.
xml = f"<payment><amount>{amount}</amount></payment>"
result = legacy_gateway.submit_xml_payment(xml)
ok = "OK" in result

# Every call site repeats this translation.
# Switch gateways later? Edit every call site.
The XML-building logic leaks into every place a payment happens — and repeats.
After — Adapter
# Client code only ever calls the clean interface.
# The translation lives in exactly one place: the adapter.
processor: PaymentProcessor = XmlGatewayAdapter(legacy_gateway)
result = processor.pay(amount_cents)

# Swap gateways by swapping the adapter — zero call
# sites change.
See the full XmlGatewayAdapter implementation below.
Client only ever talks to Target; Adapter translates each call into whatever Adaptee actually expects.

Worked example: a legacy XML payment gateway behind a modern JSON interface

# Target — what the client wants to call
class PaymentProcessor(ABC):
    @abstractmethod
    def pay(self, amount_cents: int) -> dict: ...

# Adaptee — legacy class we cannot change, XML-based
class LegacyXmlGateway:
    def submit_xml_payment(self, xml_payload: str) -> str:
        # ... calls a legacy SOAP/XML endpoint
        return "<result>OK</result>"

# Adapter — translates Target calls into Adaptee calls
class XmlGatewayAdapter(PaymentProcessor):
    def __init__(self, legacy: LegacyXmlGateway):
        self._legacy = legacy

    def pay(self, amount_cents: int) -> dict:
        xml = f"<payment><amount>{amount_cents}</amount></payment>"
        result_xml = self._legacy.submit_xml_payment(xml)
        return {"status": "ok" if "OK" in result_xml else "failed"}

# Client only ever sees PaymentProcessor
processor: PaymentProcessor = XmlGatewayAdapter(LegacyXmlGateway())
processor.pay(4999)
// Target
public interface PaymentProcessor {
    Map<String, String> pay(long amountCents);
}

// Adaptee — legacy class we cannot change
public class LegacyXmlGateway {
    public String submitXmlPayment(String xmlPayload) {
        return "<result>OK</result>";
    }
}

// Adapter
public class XmlGatewayAdapter implements PaymentProcessor {
    private final LegacyXmlGateway legacy;
    public XmlGatewayAdapter(LegacyXmlGateway legacy) { this.legacy = legacy; }

    public Map<String, String> pay(long amountCents) {
        String xml = "<payment><amount>" + amountCents + "</amount></payment>";
        String result = legacy.submitXmlPayment(xml);
        return Map.of("status", result.contains("OK") ? "ok" : "failed");
    }
}

PaymentProcessor processor = new XmlGatewayAdapter(new LegacyXmlGateway());
// Target
public interface IPaymentProcessor
{
    Dictionary<string, string> Pay(long amountCents);
}

// Adaptee — legacy class we cannot change
public class LegacyXmlGateway
{
    public string SubmitXmlPayment(string xmlPayload) => "<result>OK</result>";
}

// Adapter
public class XmlGatewayAdapter : IPaymentProcessor
{
    private readonly LegacyXmlGateway _legacy;
    public XmlGatewayAdapter(LegacyXmlGateway legacy) => _legacy = legacy;

    public Dictionary<string, string> Pay(long amountCents)
    {
        var xml = $"<payment><amount>{amountCents}</amount></payment>";
        var result = _legacy.SubmitXmlPayment(xml);
        return new() { ["status"] = result.Contains("OK") ? "ok" : "failed" };
    }
}

IPaymentProcessor processor = new XmlGatewayAdapter(new LegacyXmlGateway());
// Adapter as a hook: wraps a legacy callback-based SDK
// behind the promise-based interface the rest of the app expects.

// Adaptee — a legacy analytics SDK using callbacks, not promises
// window.legacyAnalytics.track(event, cb)

// Adapter
function useAnalytics() {
  function track(event) {
    return new Promise((resolve, reject) => {
      window.legacyAnalytics.track(event, (err, res) =>
        err ? reject(err) : resolve(res)
      );
    });
  }
  return { track }; // components only ever see this promise-based shape
}

// Client — never touches the callback API directly
function BuyButton() {
  const { track } = useAnalytics();
  return <button onClick={() => track("purchase")}>Buy</button>;
}

05 / StructuralDecorator Pattern

Structural Adds behavior without subclassing

Wraps an object to layer new behavior on top, while keeping the same interface. Classic interview prompt: coffee with add-ons — each topping wraps the previous object and adds to cost/description.

Before — no pattern
# One class, a boolean flag per topping. Every new
# topping adds a constructor param and an if-branch —
# and the combinations grow exponentially.
class Coffee:
    def __init__(self, milk=False, sugar=False):
        self.milk, self.sugar = milk, sugar

    def cost(self):
        total = 2.00
        if self.milk:  total += 0.50
        if self.sugar: total += 0.25
        return total  # whip, syrup, oat milk... this keeps growing
A 5th topping means a 5th flag, a 5th if-branch, and a class that never stops changing.
After — Decorator
# Each topping is its own class that wraps whatever
# came before it — Coffee never changes again.
drink = Milk(Sugar(Espresso()))
drink.cost()  # 2.75 — computed by delegation, layer by layer

# A new topping (Whip) is a new 5-line class,
# with zero edits to Coffee, Milk, or Sugar.
See the full Milk / Sugar decorator classes below.
Milk(Sugar(Espresso())) — each layer implements Beverage and delegates to the one it wraps.
class Beverage(ABC):
    @abstractmethod
    def cost(self) -> float: ...
    @abstractmethod
    def description(self) -> str: ...

class Espresso(Beverage):
    def cost(self): return 2.00
    def description(self): return "Espresso"

class BeverageDecorator(Beverage):
    def __init__(self, wrapped: Beverage):
        self._wrapped = wrapped

class Milk(BeverageDecorator):
    def cost(self): return self._wrapped.cost() + 0.50
    def description(self): return self._wrapped.description() + " + Milk"

class Sugar(BeverageDecorator):
    def cost(self): return self._wrapped.cost() + 0.25
    def description(self): return self._wrapped.description() + " + Sugar"

drink = Milk(Sugar(Espresso()))
print(drink.description(), drink.cost())  # Espresso + Sugar + Milk 2.75
public interface Beverage {
    double cost();
    String description();
}

public class Espresso implements Beverage {
    public double cost() { return 2.00; }
    public String description() { return "Espresso"; }
}

public abstract class BeverageDecorator implements Beverage {
    protected final Beverage wrapped;
    protected BeverageDecorator(Beverage wrapped) { this.wrapped = wrapped; }
}

public class Milk extends BeverageDecorator {
    public Milk(Beverage w) { super(w); }
    public double cost() { return wrapped.cost() + 0.50; }
    public String description() { return wrapped.description() + " + Milk"; }
}

Beverage drink = new Milk(new Espresso());
public interface IBeverage
{
    decimal Cost();
    string Description();
}

public class Espresso : IBeverage
{
    public decimal Cost() => 2.00m;
    public string Description() => "Espresso";
}

public abstract class BeverageDecorator : IBeverage
{
    protected readonly IBeverage Wrapped;
    protected BeverageDecorator(IBeverage wrapped) => Wrapped = wrapped;
    public abstract decimal Cost();
    public abstract string Description();
}

public class Milk : BeverageDecorator
{
    public Milk(IBeverage w) : base(w) { }
    public override decimal Cost() => Wrapped.Cost() + 0.50m;
    public override string Description() => Wrapped.Description() + " + Milk";
}

IBeverage drink = new Milk(new Espresso());
// Decorator maps naturally onto Higher-Order Components (HOCs)
// or composed wrapper components — each layer adds behavior
// while preserving the same rendered shape.

function withLoadingSpinner(Wrapped) {
  return function Decorated(props) {
    if (props.loading) return <Spinner />;
    return <Wrapped {...props} />;
  };
}

function withErrorBoundary(Wrapped) {
  return function Decorated(props) {
    return (
      <ErrorBoundary><Wrapped {...props} /></ErrorBoundary>
    );
  };
}

// Layered exactly like Milk(Sugar(Espresso()))
const SafeDashboard = withErrorBoundary(withLoadingSpinner(Dashboard));

06 / BehavioralStrategy Pattern

Behavioral Swaps an algorithm at runtime

Defines a family of interchangeable algorithms behind one interface, chosen by the caller. Interview staple: payment methods (credit card, PayPal, crypto) or sort/compression strategies.

Before — no pattern
# Cart knows about every payment method directly.
# Adding crypto means editing Cart's checkout method.
class Cart:
    def checkout(self, amount, method):
        if method == "card":
            return f"Charged ${amount} to card"
        elif method == "paypal":
            return f"Sent ${amount} via PayPal"
        # every new method = another elif, forever
Cart is coupled to every payment provider that ever gets added.
After — Strategy
# Cart holds a strategy object — it doesn't know or
# care which one. New methods never touch Cart.
class Cart:
    def __init__(self, strategy):
        self.strategy = strategy

    def checkout(self, amount):
        return self.strategy.pay(amount)
See the full PaymentStrategy hierarchy below.
Cart holds a PaymentStrategy reference and calls pay() — it never knows which concrete strategy it holds.
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount: float) -> str: ...

class CreditCardStrategy(PaymentStrategy):
    def pay(self, amount): return f"Charged ${amount} to card"

class PayPalStrategy(PaymentStrategy):
    def pay(self, amount): return f"Sent ${amount} via PayPal"

class Cart:
    def __init__(self, strategy: PaymentStrategy):
        self.strategy = strategy  # swappable at runtime

    def checkout(self, amount):
        return self.strategy.pay(amount)

Cart(PayPalStrategy()).checkout(49.99)
public interface PaymentStrategy {
    String pay(double amount);
}

public class CreditCardStrategy implements PaymentStrategy {
    public String pay(double amount) { return "Charged $" + amount + " to card"; }
}

public class Cart {
    private PaymentStrategy strategy; // swappable at runtime
    public Cart(PaymentStrategy strategy) { this.strategy = strategy; }

    public String checkout(double amount) { return strategy.pay(amount); }
}

new Cart(new PayPalStrategy()).checkout(49.99);

{

public class CreditCardStrategy : IPaymentStrategy

}

new Cart(new PayPalStrategy()).Checkout(49.99m);
// Strategy is just "which function do I call" — pass it as a prop.
const creditCardStrategy = (amount) => `Charged $${amount} to card`;
const paypalStrategy   = (amount) => `Sent $${amount} via PayPal`;

function Checkout({ amount, strategy }) {
  // Context (Checkout) never knows which strategy it received.
  const [result, setResult] = useState(null);
  return (
    <button onClick={() => setResult(strategy(amount))}>
      Pay {result && `— ${result}`}
    </button>
  );
}

07 / BehavioralState Pattern

Behavioral Behavior changes with internal state

An object appears to change its class as its internal state changes — each state is its own class implementing the same interface, replacing long if/elif chains on a status field. Interview staple: order lifecycle (placed → shipped → delivered) or a traffic light.

Before — no pattern
# A status string plus an if/elif chain, repeated
# everywhere the order's behavior depends on status.
class Order:
    def __init__(self):
        self.status = "placed"

    def advance(self):
        if self.status == "placed":
            self.status = "shipped"
        elif self.status == "shipped":
            self.status = "delivered"
        # every new status = another elif, and this logic
        # gets copy-pasted anywhere status is checked
The valid-transitions rule is implicit, scattered, and easy to get wrong.
After — State
# Each status is its own class; Order just delegates.
# Invalid transitions become structurally impossible.
class Order:
    def __init__(self):
        self.state = Placed()

    def advance(self):
        self.state.next(self)
See the full Placed / Shipped / Delivered classes below.
Order delegates to its current state object; calling next() swaps in the following state.
class OrderState(ABC):
    @abstractmethod
    def next(self, order): ...
    @abstractmethod
    def name(self) -> str: ...

class Placed(OrderState):
    def next(self, order): order.state = Shipped()
    def name(self): return "placed"

class Shipped(OrderState):
    def next(self, order): order.state = Delivered()
    def name(self): return "shipped"

class Delivered(OrderState):
    def next(self, order): pass  # terminal
    def name(self): return "delivered"

class Order:
    def __init__(self):
        self.state: OrderState = Placed()  # behavior lives in the state object

    def advance(self):
        self.state.next(self)
public interface OrderState {
    void next(Order order);
    String name();
}

public class Placed implements OrderState {
    public void next(Order o) { o.setState(new Shipped()); }
    public String name() { return "placed"; }
}

public class Shipped implements OrderState {
    public void next(Order o) { o.setState(new Delivered()); }
    public String name() { return "shipped"; }
}

public class Order {
    private OrderState state = new Placed(); // behavior lives in the state object
    public void advance() { state.next(this); }
    public void setState(OrderState s) { state = s; }
}
public interface IOrderState
{
    void Next(Order order);
    string Name { get; }
}

public class Placed : IOrderState
{
    public void Next(Order o) => o.State = new Shipped();
    public string Name => "placed";
}

public class Shipped : IOrderState
{
    public void Next(Order o) => o.State = new Delivered();
    public string Name => "shipped";
}

public class Order
{
    public IOrderState State { get; set; } = new Placed(); // behavior lives here
    public void Advance() => State.Next(this);
}
// State pattern in React usually surfaces as a state machine —
// each state maps to what's rendered AND what actions are valid.

const transitions = {
  placed:    { next: "shipped" },
  shipped:   { next: "delivered" },
  delivered: { next: null }, // terminal
};

function useOrderState(initial = "placed") {
  const [state, setState] = useState(initial);
  const advance = () => {
    const next = transitions[state].next;
    if (next) setState(next); // only valid transitions are reachable
  };
  return { state, advance };
}

function OrderTracker() {
  const { state, advance } = useOrderState();
  return <button onClick={advance}>Status: {state}</button>;
}
Strategy vs. State — the interview trap

Same UML shape (context holds an interface, concrete classes implement it). The difference is intent: Strategy is chosen once by the caller and doesn't change itself; State is switched by the object itself as a reaction to its own lifecycle.

08 / BehavioralObserver Pattern

Behavioral One-to-many change notification

A subject maintains a list of dependents and notifies them automatically of any state change. Interview staple: stock ticker, event emitters, or any pub/sub system.

Before — no pattern
# StockTicker calls each interested piece of code by name.
# Adding a new listener means editing set_price itself.
class StockTicker:
    def set_price(self, price):
        self.price = price
        price_display.update(price)   # hardcoded
        price_logger.update(price)    # hardcoded
        # new listener? another line here, every time
StockTicker must know every listener's name and type up front.
After — Observer
# Listeners register themselves; StockTicker just
# iterates whoever's attached, without knowing who.
class StockTicker:
    def set_price(self, price):
        self.price = price
        for obs in self._observers:
            obs.update(price)
See the full attach() / Observer mechanics below.
StockTicker holds many Observers and pushes updates to all of them on price change.
class Observer(ABC):
    @abstractmethod
    def update(self, price: float): ...

class StockTicker:
    def __init__(self):
        self._observers: list[Observer] = []

    def attach(self, observer: Observer):
        self._observers.append(observer)

    def set_price(self, price: float):
        self._price = price
        for obs in self._observers:
            obs.update(price)  # push to every subscriber

class PriceDisplay(Observer):
    def update(self, price):
        print(f"Price is now ${price}")

ticker = StockTicker()
ticker.attach(PriceDisplay())
ticker.set_price(182.50)
public interface Observer {
    void update(double price);
}

public class StockTicker {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer o) { observers.add(o); }

    public void setPrice(double price) {
        for (Observer o : observers) o.update(price); // push to every subscriber
    }
}

public class PriceDisplay implements Observer {
    public void update(double price) { System.out.println("Price is now $" + price); }
}

StockTicker ticker = new StockTicker();
ticker.attach(new PriceDisplay());
ticker.setPrice(182.50);
// C# idiomatic Observer: built-in event + delegate
public class StockTicker
{
    public event Action<double> PriceChanged; // the "Subject" interface, built in

    public void SetPrice(double price) =>
        PriceChanged?.Invoke(price); // push to every subscriber
}

var ticker = new StockTicker();
ticker.PriceChanged += price => Console.WriteLine($"Price is now ${price}");
ticker.SetPrice(182.50);
// Observer is React's native data flow: state changes in a
// provider, every subscribed component re-renders automatically.

const PriceContext = createContext(null);

function StockTickerProvider({ children }) {
  const [price, setPrice] = useState(180.00); // the Subject's state
  return (
    <PriceContext.Provider value={{ price, setPrice }}>
      {children} // every consumer below is an Observer
    </PriceContext.Provider>
  );
}

function PriceDisplay() {
  const { price } = useContext(PriceContext); // auto re-renders on change
  return <p>Price is now ${price}</p>;
}

09 / CreationalFactory Pattern

Creational Delegates object creation

Defines an interface for creating an object, letting subclasses (or a single method) decide which concrete class to instantiate. Interview staple: shape/notification factories where the caller asks for a type string and gets back the right class.

Before — no pattern
# Every call site that sends a notification repeats
# the same "which class do I construct?" branching.
if kind == "email":
    n = EmailNotification()
elif kind == "sms":
    n = SmsNotification()
n.send("Order shipped")
# ...and this exact branching is copy-pasted at
# every other call site that also sends notifications
The construction logic is duplicated everywhere a notification gets created.
After — Factory
# Construction logic lives in exactly one place.
# Call sites just ask for what they want.
NotificationFactory.create("sms").send("Order shipped")

# A new kind is one new branch, in one place —
# every call site stays untouched.
See the full NotificationFactory below.
Caller asks the factory for a Notification by type; the factory alone knows which concrete class to build.
class Notification(ABC):
    @abstractmethod
    def send(self, message: str): ...

class EmailNotification(Notification):
    def send(self, message): print(f"Email: {message}")

class SmsNotification(Notification):
    def send(self, message): print(f"SMS: {message}")

class NotificationFactory:
    @staticmethod
    def create(kind: str) -> Notification:
        if kind == "email": return EmailNotification()
        if kind == "sms":   return SmsNotification()
        raise ValueError(f"Unknown kind: {kind}")

# Caller never calls a constructor directly
NotificationFactory.create("sms").send("Order shipped")
public interface Notification {
    void send(String message);
}

public class EmailNotification implements Notification {
    public void send(String m) { System.out.println("Email: " + m); }
}

public class SmsNotification implements Notification {
    public void send(String m) { System.out.println("SMS: " + m); }
}

public class NotificationFactory {
    public static Notification create(String kind) {
        return switch (kind) {
            case "email" -> new EmailNotification();
            case "sms"   -> new SmsNotification();
            default -> throw new IllegalArgumentException(kind);
        };
    }
}

// Caller never calls a constructor directly
NotificationFactory.create("sms").send("Order shipped");

{
    void Send(string message);
}

// Factory as a component-selector function — very common for
// rendering polymorphic content (form fields, notification toasts).

const registry = {
  email: EmailNotification,
  sms: SmsNotification,
};

function NotificationFactory({ kind, ...props }) {
  const Component = registry[kind];
  if (!Component) throw new Error(`Unknown kind: ${kind}`);
  return <Component {...props} />; // caller never imports EmailNotification directly
}
